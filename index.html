01

The decision

Gyrus is a broker platform built against the Duck Creek API. We want a Snowflake warehouse for reporting. The only unsettled question is how data physically gets from Duck Creek into it.

Three routes were raised informally: direct SQL access to their database, direct access to their warehouse, or file exports we load ourselves. Research surfaced two more, one of which is materially better than all three.

This document is written to be followed, not just read. §02 explains the Snowflake concepts you need if you have never used it. §04 covers the work that is identical no matter which route wins — start there. §05 to §09 walk through each route step by step, with every command explained and the failure it prevents named. §14 is the selection framework.

Scope

Duck Creek data only. Gyrus also holds its own application data — users, in-progress quotes, journey events, audit trail — in a database we control outright. That needs nobody’s permission and is where §15 says to start.

02

Snowflake in ten minutes

If you have used Postgres or SQL Server, most of Snowflake is familiar. Four things are not, and every route below depends on them.

2.1  Compute is separate from storage

In Postgres, the server that stores your data is the same server that runs your queries. Snowflake splits these completely.

Your data sits once in cloud object storage, compressed and organised column by column. Queries are executed by a virtual warehouse — an independent compute cluster you start, size, and stop. Several warehouses can read the same tables at the same time with no contention, because none of them owns the data.

The word that confuses everyone

A Snowflake warehouse is not a database. It is a compute cluster — closer to an EC2 auto-scaling group. Data lives in databases; queries are executed by warehouses. When this document says TRANSFORM_WH, that is CPU, not storage.

Three consequences matter for us:

  • You pay per second a warehouse runs, and nothing when it is suspended. Cost control is mostly about not leaving them running — hence AUTO_SUSPEND on everything.
  • Sizes double. XSMALL → SMALL → MEDIUM each doubles compute and hourly cost, but also roughly halves runtime on a big scan — so cost per query is often similar. A bigger warehouse mainly buys speed.
  • Give each workload its own warehouse. An analyst’s runaway query then cannot slow ingestion, and per-warehouse billing tells you exactly which workload costs what.

2.2  Permissions attach to roles, never to users

You do not grant a privilege to a person. You grant it to a role, then grant the role to a user. A session activates one role at a time, and roles can be granted to other roles to form a hierarchy.

Built-in roles run from ACCOUNTADMIN (billing, account settings — use rarely) through SECURITYADMIN (users and roles) to SYSADMIN (creates databases, schemas, warehouses — owns your data objects). We create three custom roles on top: LOADER, TRANSFORMER, ANALYST.

The grant mistake everyone makes once

GRANT SELECT ON ALL TABLES IN SCHEMA … applies only to tables that exist at the moment you run it. Tables created tomorrow are not covered. You also need GRANT SELECT ON FUTURE TABLES …, or every new table is invisible to your analysts and you re-run grants forever without understanding why.

2.3  Loading files: four objects that work together

Routes B and D load files. Snowflake models this with four objects, and understanding how they chain together makes §06 straightforward.

ObjectWhat it isAnalogy

One more object matters: a directory table on a stage makes the file listing queryable in SQL. That is what lets us detect a file that never arrived (§06, step 8).

2.4  Load raw first, transform in SQL (ELT)

The older pattern, ETL, transformed data on a separate machine before loading it, because warehouses were fixed-size appliances whose compute was too scarce to spend on cleaning.

Snowflake’s compute is elastic and billed per second, so we invert it. ELT lands data exactly as it arrives, then transforms it with SQL inside the warehouse. Three schemas result:

LayerContainsRule
RAWExactly what arrived. Original column names. Text columns where the source is untyped. Provenance on every row.Append-only. Never edit, never clean.
STAGINGOne view per source object: renamed, typed, deduplicated, deletes filtered, timestamps in UTC.No joins, no aggregation, no business logic.
MARTSBusiness models — facts and dimensions the BI tool reads.Never read RAW directly; always via STAGING.

A useful way to hold it: RAW is your commit history; STAGING and MARTS are build output. You would never edit git history to fix a bug — you fix the code and rebuild. Same here. When a transform turns out to be wrong, you rewrite SQL and rebuild from RAW rather than asking Duck Creek to re-send last March.

That last point is why ELT matters more for file and API routes than for database replication: you often cannot re-request the source data, so destroying it during load is unrecoverable.

Step 1

Create the database and its five schemas

A Snowflake database is a namespace, not a server. Inside it, schemas group related objects. We use five, and the split is deliberate: one RAW schema per source system so the two never collide, plus an ADMIN schema for the bookkeeping tables that make the pipeline auditable.

Run as SYSADMIN
USE ROLE SYSADMIN;

CREATE DATABASE IF NOT EXISTS GYRUS_DW;

CREATE SCHEMA IF NOT EXISTS GYRUS_DW.RAW_DUCKCREEK;  -- whichever route wins
CREATE SCHEMA IF NOT EXISTS GYRUS_DW.RAW_GYRUS;      -- our own app database
CREATE SCHEMA IF NOT EXISTS GYRUS_DW.STAGING;        -- cleaned views
CREATE SCHEMA IF NOT EXISTS GYRUS_DW.MARTS;          -- business models
CREATE SCHEMA IF NOT EXISTS GYRUS_DW.ADMIN;          -- manifests, calendars, controls

Why two RAW schemas. Both systems will have a table called something like POLICY. Separate schemas mean no collision, and it stays obvious at a glance which system any table came from — which matters enormously when a number looks wrong and you are tracing it back.

Step 2

Create three warehouses, one per workload

Remember from §2.1 that a warehouse is compute. We create three so the workloads cannot interfere with each other, and so the bill tells us which one costs what.

Compute
CREATE WAREHOUSE IF NOT EXISTS LOAD_WH
  WAREHOUSE_SIZE = 'XSMALL'  -- ingestion is I/O bound, not CPU bound
  AUTO_SUSPEND   = 60         -- suspend after 60s idle
  AUTO_RESUME    = TRUE       -- wake automatically on next query
  INITIALLY_SUSPENDED = TRUE; -- do not start billing on creation

CREATE WAREHOUSE IF NOT EXISTS TRANSFORM_WH
  WAREHOUSE_SIZE = 'SMALL'   -- joins and aggregates need more
  AUTO_SUSPEND = 60 AUTO_RESUME = TRUE INITIALLY_SUSPENDED = TRUE;

CREATE WAREHOUSE IF NOT EXISTS BI_WH
  WAREHOUSE_SIZE = 'SMALL'
  AUTO_SUSPEND = 300          -- longer: analysts query in bursts
  AUTO_RESUME = TRUE INITIALLY_SUSPENDED = TRUE;

Why the different AUTO_SUSPEND values. 60 seconds suits scheduled jobs that run and finish. 300 suits interactive use, where a 60-second suspend means an analyst pauses to think and pays a cold start when they resume. Going below 60 anywhere causes repeated cold starts that cost more than the idle time saved.

If you skip INITIALLY_SUSPENDED the warehouse starts running the moment it is created and bills until something suspends it. On a Friday afternoon that is a whole weekend of compute for nothing.

Step 3

Set Time Travel retention deliberately

Time Travel lets you query a table as it was N days ago. It is billed, because Snowflake keeps the old versions. The right retention differs by layer.

Retention
ALTER SCHEMA GYRUS_DW.RAW_DUCKCREEK SET DATA_RETENTION_TIME_IN_DAYS = 1;
ALTER SCHEMA GYRUS_DW.MARTS          SET DATA_RETENTION_TIME_IN_DAYS = 7;

Why RAW gets only one day. RAW is a replica of something that exists elsewhere — the source system, or the file archive in S3. If we lose it we reload it. MARTS gets seven days because rebuilding derived models takes compute and someone’s afternoon.

Step 4

Create roles and grant privileges — including FUTURE

Three roles matching the three layers. LOADER writes RAW. TRANSFORMER reads RAW and owns STAGING and MARTS. ANALYST reads MARTS only.

Roles and grants
USE ROLE USERADMIN;
CREATE ROLE IF NOT EXISTS LOADER;
CREATE ROLE IF NOT EXISTS TRANSFORMER;
CREATE ROLE IF NOT EXISTS ANALYST;

USE ROLE SECURITYADMIN;
-- Grant to SYSADMIN so administrators inherit everything below
GRANT ROLE LOADER      TO ROLE SYSADMIN;
GRANT ROLE TRANSFORMER TO ROLE SYSADMIN;
GRANT ROLE ANALYST     TO ROLE SYSADMIN;

USE ROLE SYSADMIN;

-- TRANSFORMER: read everything, own the modelling layers
GRANT USAGE  ON DATABASE GYRUS_DW TO ROLE TRANSFORMER;
GRANT USAGE  ON ALL SCHEMAS    IN DATABASE GYRUS_DW TO ROLE TRANSFORMER;
GRANT USAGE  ON FUTURE SCHEMAS IN DATABASE GYRUS_DW TO ROLE TRANSFORMER;
GRANT SELECT ON ALL TABLES     IN DATABASE GYRUS_DW TO ROLE TRANSFORMER;
GRANT SELECT ON FUTURE TABLES  IN DATABASE GYRUS_DW TO ROLE TRANSFORMER;
GRANT ALL    ON SCHEMA GYRUS_DW.STAGING TO ROLE TRANSFORMER;
GRANT ALL    ON SCHEMA GYRUS_DW.MARTS   TO ROLE TRANSFORMER;
GRANT USAGE  ON WAREHOUSE TRANSFORM_WH TO ROLE TRANSFORMER;

-- ANALYST: read-only on the business layer
GRANT USAGE  ON DATABASE GYRUS_DW TO ROLE ANALYST;
GRANT USAGE  ON SCHEMA GYRUS_DW.MARTS TO ROLE ANALYST;
GRANT SELECT ON ALL TABLES    IN SCHEMA GYRUS_DW.MARTS TO ROLE ANALYST;
GRANT SELECT ON FUTURE TABLES IN SCHEMA GYRUS_DW.MARTS TO ROLE ANALYST;
GRANT SELECT ON FUTURE VIEWS  IN SCHEMA GYRUS_DW.MARTS TO ROLE ANALYST;
GRANT USAGE  ON WAREHOUSE BI_WH TO ROLE ANALYST;

Note the role switching. USERADMIN creates roles, SECURITYADMIN grants roles to roles, SYSADMIN grants privileges on objects it owns. Running all of this as ACCOUNTADMIN appears to work but creates objects owned by the wrong role, which causes confusing permission failures weeks later.

The FUTURE lines are not optional. Without them, every table created after today is invisible to TRANSFORMER and ANALYST. The symptom is baffling: the table plainly exists, but the analyst gets “object does not exist or not authorized”.

Verify before moving on

Two minutes now saves an afternoon later.

Checks

SHOW SCHEMAS IN DATABASE GYRUS_DW;

-- Are the warehouses suspended (not burning credits)?
SHOW WAREHOUSES;   -- state column should read SUSPENDED

4.6  The staging pattern you will repeat for every table

This shape recurs for every source object regardless of route. Read it once carefully — later sections refer back to it rather than repeating it.

It has four jobs: pick one winning row per key, cast text into real types safely, clean the values, and drop rows that should not be there.

The canonical staging view
CREATE OR REPLACE VIEW GYRUS_DW.STAGING.STG_POLICY AS
SELECT
    TRIM(policy_id)                              AS policy_id,
    UPPER(TRIM(broker_ref))                      AS broker_ref,
    UPPER(TRIM(status))                          AS policy_status,

    TRY_TO_NUMBER(
      REPLACE(REPLACE(TRIM(gross_premium), ',', ''), '$', '')
    , 18, 2)                                    AS gross_premium,

    TRY_TO_DATE(TRIM(effective_date), 'YYYY-MM-DD') AS effective_date,
    CONVERT_TIMEZONE('UTC', updated_at)          AS updated_at_utc,

    _source_ref, _load_ts                       -- provenance, always carried
FROM GYRUS_DW.RAW_DUCKCREEK.POLICY
WHERE TRIM(COALESCE(policy_id, '')) <> ''
QUALIFY ROW_NUMBER() OVER (
    PARTITION BY TRIM(policy_id)
    ORDER BY _load_ts DESC) = 1;

Four decisions in that view are load-bearing. Each exists because its absence produces wrong numbers rather than an error, which is the hardest class of bug to find.

DecisionWhat it doesWhat happens without it
TRY_TO_NUMBER
TRY_TO_DATE		Returns NULL when a value cannot be converted, instead of raising an error.The bare TO_NUMBER aborts the whole query on one bad cell. A single "N/A" in a premium column breaks every report.
QUALIFY ROW_NUMBER()Keeps only the newest row per key. Filters on a window function without needing a subquery.Re-delivered files, replayed API pages and reloaded extracts all duplicate. Totals silently double.

5.1  What data sharing actually is

This is the concept most people have not met before, so it is worth being precise.

In Snowflake, a share is an object a provider account creates that names some tables and views, plus a list of consumer accounts allowed to read them. When a consumer mounts a share, Snowflake creates a read-only database in the consumer’s account that points at the provider’s storage. No bytes are copied. No pipeline runs. No schedule exists.

Your queries run on your warehouse (so you pay the compute), against their storage (so they pay the storage). When they update a row, your next query sees it — because there is only one copy and you are reading it directly.

Two conditions must hold. Both are Q2 and Q3 in §16:

  • Duck Creek must be willing to create the share and add our account to it — a product and contract question, not a technical one.
  • Both accounts must be in the same cloud region. If not, the provider has to replicate the data to our region first, which costs them money and requires their agreement.

5.2  Implementation, step by step

Step 1

Give Duck Creek our account identifier

They need to know which account to add to the share. Send them the value below, not the browser URL — the URL is not always the identifier and this is a common source of a wasted round trip.

Find our identifier
SELECT CURRENT_ORGANIZATION_NAME() AS org,
       CURRENT_ACCOUNT_NAME()      AS account,
       CURRENT_REGION()            AS region;

Send the region too. It lets them tell you immediately whether replication is needed, rather than discovering it after provisioning.

Step 2

Confirm the share has arrived

Once they add us, the share appears in our account automatically. Nothing needs installing.

Inspect the inbound share
USE ROLE ACCOUNTADMIN;   -- or any role holding IMPORT SHARE

SHOW SHARES;              -- kind = INBOUND is one offered to us

-- What is actually in it? Do this before mounting.
DESC SHARE DUCKCREEK_ACCT.CLARITY_SHARE;

DESC SHARE lists every object the share exposes. Check it against the entity list from Q4 before going further — if a table you need for §11 is missing, that is a conversation to have now, not after you have built models on top.

Step 3

Mount the share as a database

One statement. This is the entire ingestion build for this route.

Mount and grant
CREATE DATABASE DUCKCREEK_CLARITY
  FROM SHARE DUCKCREEK_ACCT.CLARITY_SHARE;

-- Shared databases use IMPORTED PRIVILEGES, not the usual GRANT SELECT
GRANT IMPORTED PRIVILEGES ON DATABASE DUCKCREEK_CLARITY TO ROLE TRANSFORMER;

SELECT COUNT(*) FROM DUCKCREEK_CLARITY.PUBLIC.POLICY;   -- it just works

IMPORTED PRIVILEGES is the part people get wrong. You cannot GRANT SELECT ON … individual shared tables — the provider owns them. You grant the imported privileges on the whole shared database instead, and access to individual objects follows from what the provider put in the share.

Compare with Route B, which needs a bucket, an IAM trust relationship, a storage integration, a file format, a stage, a pipe, an event notification, a manifest table, a calendar table and four monitoring views before a single row lands.

Step 4

Build staging views on top — exactly as in §4.6

From here nothing is special. The shared database behaves like any other source for reading purposes.

Staging over shared data
USE ROLE TRANSFORMER;

CREATE OR REPLACE VIEW GYRUS_DW.STAGING.STG_POLICY AS
SELECT
    TRIM(policy_id)                      AS policy_id,
    UPPER(TRIM(broker_ref))              AS broker_ref,
    UPPER(TRIM(status))                  AS policy_status,
    gross_premium,                          -- already typed by Clarity
    CONVERT_TIMEZONE('UTC', updated_at)  AS updated_at_utc
FROM DUCKCREEK_CLARITY.PUBLIC.POLICY;

This staging view is much thinner than the file-route equivalent, and that is a real advantage of Route A. Clarity data is already typed and modelled for insurance, so there is no text-to-number casting, no total-row filtering, and no deduplication to do — the provider has done it.

5.3  The constraints that bite — read before designing

Shared objects are not ordinary tables, and several limitations only surface once you build on them. None is a reason to reject the route; all of them shape the design.

AS

A design call to make early, not late

Pure sharing is cheapest and simplest. Sharing plus a nightly snapshot costs storage but restores Time Travel, cloning, point-in-time history, and a copy that survives revocation. For a regulated insurance dataset the snapshot is probably worth its cost — but decide deliberately rather than discovering the gap during an audit.

Remember this line

ALTER TASK … RESUME. Every task in Snowflake is created suspended. Forgetting it is the single most common cause of “the pipeline is not running and there is no error anywhere”.

6.1  What you are building, in plain terms

Duck Creek runs a scheduled export and writes a file to a bucket we own. The moment the file lands, S3 sends an event to Snowflake, and Snowflake loads it. Nobody presses anything.

The build has three parts, and it is worth holding them separately in your head:

  • The landing zone — a bucket with three folders and a lifecycle policy (steps 1–2).
  • The load path — integration, format, stage, table, pipe (steps 3–7).
  • The control plane — manifest, calendar, reconciliation, alerting (step 8). This is the part teams skip, and it is the part that makes the difference between a pipeline and a script.
The thing to understand before you start

A file export gives you a snapshot, not a change stream. It tells you what the data looked like at export time, never what changed. That has two consequences that shape everything below: deletes are invisible (§10), and a file that never arrives looks exactly like a normal day — the dashboard renders, the query succeeds, and the numbers are simply yesterday’s.

6.2  Implementation, step by step

Step 1

Agree the data contract before writing any code

This is the highest-value hour in the whole route, and the one most often skipped. With a database, the schema is the contract and the engine enforces it. With files, nothing enforces anything unless it is written down and agreed.

Get a one-page agreement per report covering: delivery schedule and time, exact bucket path, format and encoding, header row, grain (one row per what?), whether it is a full snapshot or a delta, date format, decimal separator, how nulls are written, the filename convention, control totals, the restatement policy, and how much notice we get before a column changes.

The filename convention — do not negotiate this away
policy_20260824_070500.csv
│      │        │
│      │        └── export time — resolves ordering and re-issues
│      └─────────── business date the data represents
└────────────────── report identity

Why the filename matters so much. It is the only metadata we control without opening the file. It gives us identity, period and version — which is what makes “a corrected file arrived, which one wins?” answerable in SQL rather than by a human.

Push hardest for two things: CSV or Parquet rather than Excel, and control totals — a row count and key column sums delivered alongside each file. Control totals are the difference between hoping a load worked and knowing it did.

Step 2

Build the landing zone

Three folders, three states. This separation is what makes the pipeline debuggable when something breaks at 2am.

Bucket layout and policy
s3://gyrus-dc-landing/
├── inbound/policy/      policy_20260824_070500.csv   # evidence — immutable
├── normalised/policy/   policy_20260824_070500.parquet # derived — regenerable
└── rejected/policy/                                  # failed — needs a human

# Versioning ON, SSE encryption, public access blocked
# Lifecycle: STANDARD_IA at 90d, GLACIER at 365d — and NO expiration rule
# Producer IAM policy: s3:PutObject on inbound/* ONLY. No read. No delete.

Write-only producer credentials mean a mistake on Duck Creek’s side cannot destroy our history. They can add files; they cannot overwrite or remove them.

No expiration rule, deliberately. Storage is cheap. A lost source file is unrecoverable — you cannot ask a vendor to re-run last March’s export and expect the same numbers. Treat every landed file as evidence you may need in a dispute two years from now.

Step 3

Let Snowflake read the bucket

A storage integration holds the IAM trust configuration. It is a two-sided handshake: you create it in Snowflake, read two generated values out of it, and paste those into the AWS role’s trust policy.

Snowflake side
USE ROLE ACCOUNTADMIN;

CREATE OR REPLACE STORAGE INTEGRATION s3_dc_int
  TYPE = EXTERNAL_STAGE
  STORAGE_PROVIDER = 'S3'
  ENABLED = TRUE
  STORAGE_AWS_ROLE_ARN = 'arn:aws:iam::<acct>:role/snowflake-gyrus-role'
  STORAGE_ALLOWED_LOCATIONS = ('s3://gyrus-dc-landing/');

-- Copy STORAGE_AWS_IAM_USER_ARN and STORAGE_AWS_EXTERNAL_ID from this output
DESC INTEGRATION s3_dc_int;

GRANT USAGE ON INTEGRATION s3_dc_int TO ROLE LOADER;

Then on the AWS side, the role’s trust policy allows that IAM user to assume it, conditioned on that external ID:

AWS trust policy

    "Action": "sts:AssumeRole",
    "Condition": {

  }]
}

Why this rather than access keys. No AWS secret ever enters Snowflake. Access is granted by role assumption and can be revoked entirely from the AWS side, without touching Snowflake.

If LIST later returns nothing, the cause is almost always here: the external ID was regenerated (it changes if you recreate the integration), or the allowed-locations prefix does not match the bucket path.

Step 4

Define how to parse the files

A file format object captures every parsing decision once. Most CSV pain is solved here, so it is worth understanding each option rather than copying the block.

File format
USE ROLE LOADER;

CREATE OR REPLACE FILE FORMAT GYRUS_DW.RAW_DUCKCREEK.ff_dc_csv
  TYPE = CSV
  PARSE_HEADER = TRUE
  FIELD_DELIMITER = ','
  FIELD_OPTIONALLY_ENCLOSED_BY = '"'
  TRIM_SPACE = TRUE
  ENCODING = 'UTF8'
  NULL_IF = ('', 'NULL', 'null', 'N/A', '#N/A', '#REF!', '#DIV/0!', '-')
  EMPTY_FIELD_AS_NULL = TRUE
  REPLACE_INVALID_CHARACTERS = TRUE
  ESCAPE_UNENCLOSED_FIELD = NONE;
OptionWhy it is set that way
PARSE_HEADER = TRUEReads column names from row 1, which is what enables name-based loading in step 6. Cannot be combined with SKIP_HEADER — setting both is an error.
FIELD_OPTIONALLY_ENCLOSED_BYWithout it, one comma inside a value — a company name, an address — shifts every subsequent field on that row. Also handles newlines inside quoted fields.
NULL_IFTurns spreadsheet placeholders and formula errors into real nulls. Without it, #DIV/0! is stored as literal text in a premium column.
TRIM_SPACERemoves trailing spaces that fixed-width exports add. 'ACTIVE   ' does not equal 'ACTIVE'.
REPLACE_INVALID_CHARACTERSOne bad byte replaces a character rather than failing the whole file.
ESCAPE_UNENCLOSED_FIELD = NONEStops backslashes in data being interpreted as escape sequences — a surprise that corrupts address and reference fields.

Create the stage, then look at a real file

The stage points at the bucket. DIRECTORY = (ENABLE = TRUE) makes the file listing queryable in SQL, which step 8 depends on.

Stage and inspection

  STORAGE_INTEGRATION = s3_dc_int

Do not trust INFER_SCHEMA blindly. It will happily type a policy reference with leading zeros as a NUMBER, destroying the zeros, or pick a numeric precision that overflows next quarter. Use it as a draft, not an answer.

Step 6

Create the RAW table — every business column as text

This looks wrong the first time you see it. It is the single most useful convention in file-based ingestion.

RAW table
CREATE OR REPLACE TABLE GYRUS_DW.RAW_DUCKCREEK.POLICY_EXTRACT (
    policy_id            VARCHAR,     -- named exactly as the file header
    broker_ref           VARCHAR,
    status               VARCHAR,
    gross_premium        VARCHAR,     -- yes, text
    effective_date       VARCHAR,     -- yes, text

    _file_name           VARCHAR,     -- provenance: which file
    _file_row_number     NUMBER,      -- which line in it
    _file_last_modified  TIMESTAMP_NTZ,
    _load_ts             TIMESTAMP_LTZ -- when we loaded it
);

Why text. A typed column fails the entire file on one bad value. One "N/A" in a premium field, one "31/02/2026", and the whole day’s load aborts — usually overnight, usually discovered by an analyst the next morning.

As text, the load always succeeds. Bad values become an isolated, queryable data-quality finding (step 8) that you can send back to Duck Creek with the exact file and line number, while the other 99.9% of the data is available for reporting.

The provenance columns are not optional. They are what make the warehouse auditable, and step 8’s deduplication and reconciliation both depend on them.

Step 7

Load once by hand, then automate with a pipe

Get a manual load working before creating a pipe. Debugging COPY INTO interactively is far easier than debugging something that runs on an event you cannot trigger at will.

Manual load
-- Dry run first: parses and reports errors, writes nothing
COPY INTO GYRUS_DW.RAW_DUCKCREEK.POLICY_EXTRACT
FROM @stg_dc/inbound/policy/
FILE_FORMAT = (FORMAT_NAME = 'ff_dc_csv')
MATCH_BY_COLUMN_NAME = CASE_INSENSITIVE
VALIDATION_MODE = 'RETURN_ERRORS';

-- Then for real
COPY INTO GYRUS_DW.RAW_DUCKCREEK.POLICY_EXTRACT
FROM @stg_dc/inbound/policy/
FILE_FORMAT = (FORMAT_NAME = 'ff_dc_csv')
MATCH_BY_COLUMN_NAME = CASE_INSENSITIVE
INCLUDE_METADATA = (
    _file_name          = METADATA$FILENAME,
    _file_row_number    = METADATA$FILE_ROW_NUMBER,
    _file_last_modified = METADATA$FILE_LAST_MODIFIED,
    _load_ts            = METADATA$START_SCAN_TIME
)
ON_ERROR = ABORT_STATEMENT;
MATCH_BY_COLUMN_NAME is the most important option on this page

Without it, COPY INTO loads columns by position. The day Duck Creek reorders their export — and eventually they will, without telling anyone — premiums land in the status column, statuses land in the date column, and the load reports success. Every downstream number is wrong and nothing anywhere raises an error. This one option prevents that entire class of failure.

Choosing ON_ERROR:

  • ABORT_STATEMENT — fail the whole load on the first bad row. Right for manual loads: loud and obvious.
  • SKIP_FILE — skip the offending file, continue with others. Right for a pipe, where one bad file must not block the queue.
  • CONTINUE — load good rows, drop bad ones. Avoid. It discards data silently, which is the failure mode this whole design exists to prevent.
Automate
CREATE OR REPLACE PIPE GYRUS_DW.RAW_DUCKCREEK.pipe_policy
  AUTO_INGEST = TRUE
AS
COPY INTO GYRUS_DW.RAW_DUCKCREEK.POLICY_EXTRACT
FROM @stg_dc/inbound/policy/

MATCH_BY_COLUMN_NAME = CASE_INSENSITIVE
INCLUDE_METADATA = (_file_name = METADATA$FILENAME,
                    _file_row_number = METADATA$FILE_ROW_NUMBER,
                    _load_ts = METADATA$START_SCAN_TIME)
ON_ERROR = SKIP_FILE;

-- Take notification_channel (an SQS ARN) from here...
SHOW PIPES LIKE 'pipe_policy';
-- ...and set it as the destination of an S3 event notification on the bucket,
--    filtered to prefix inbound/policy/ and suffix .csv

SELECT SYSTEM$PIPE_STATUS('GYRUS_DW.RAW_DUCKCREEK.pipe_policy');
-- executionState should read RUNNING; pendingFileCount rises then falls on upload

Snowpipe is serverless. It does not use LOAD_WH — it is billed per file plus compute-seconds. That means many tiny files cost far more than a few large ones, which is worth raising with Duck Creek if they propose per-transaction exports.

Event notifications only fire for new objects. Files already sitting in the bucket when you create the pipe will never load. Use ALTER PIPE … REFRESH to queue the last 7 days, and a one-off COPY INTO for anything older.

Idempotency is free — for 64 days

Snowflake records which files it has already loaded into each table and skips them, so re-running a load will not duplicate rows. That record is kept for 64 days only. A file re-delivered after that window loads again and duplicates silently. This is exactly why step 8 keeps our own manifest instead of relying on the built-in behaviour.

Step 8

Build the control plane — do not treat this as optional

Everything above moves data. This is what tells you whether the data is right. File pipelines fail quietly, and each object here exists because its absence produces confidently wrong numbers rather than an error.

Manifest

8b. Detect the file that never came. To notice something is absent you must know it was expected, which needs a calendar table.

Missing-file alerting
CREATE TABLE IF NOT EXISTS GYRUS_DW.ADMIN.EXPECTED_FILES (
    report_name VARCHAR, business_date DATE,
    expected_by TIMESTAMP_NTZ, is_business_day BOOLEAN
);

CREATE OR REPLACE VIEW GYRUS_DW.ADMIN.V_MISSING_FILES AS
SELECT e.report_name, e.business_date, e.expected_by,
       DATEDIFF('hour', e.expected_by, CURRENT_TIMESTAMP()) AS hours_overdue
FROM GYRUS_DW.ADMIN.EXPECTED_FILES e
LEFT JOIN GYRUS_DW.ADMIN.LOAD_MANIFEST m
       ON m.report_name = e.report_name AND m.business_date = e.business_date
WHERE e.is_business_day
  AND e.expected_by < CURRENT_TIMESTAMP()
  AND m.file_name IS NULL;

-- Fail loudly so existing alerting picks it up
CREATE OR REPLACE TASK GYRUS_DW.ADMIN.CHECK_MISSING
  WAREHOUSE = TRANSFORM_WH
  SCHEDULE  = 'USING CRON 0 9 * * MON-FRI Australia/Sydney'  -- 2h after SLA
AS
DECLARE missing INTEGER;
BEGIN
  SELECT COUNT(*) INTO missing FROM GYRUS_DW.ADMIN.V_MISSING_FILES;
  IF (missing > 0) THEN RAISE STATEMENT_ERROR; END IF;
END;

ALTER TASK GYRUS_DW.ADMIN.CHECK_MISSING RESUME;
Why this is the most important alert in the pipeline

Every other check tells you data is bad. This one tells you there is no data — which otherwise presents as dashboards rendering perfectly with yesterday’s figures. No error, no failed job, nothing red. People make decisions on stale numbers for days. Test it by deliberately skipping a delivery before you call the pipeline done.

8c. Reconcile against their totals, and surface cast failures.

Reconciliation and data quality
-- Did we load what they said they sent? (needs control totals from step 1)
SELECT m.business_date, m.rows_loaded, m.control_rows,
       m.rows_loaded - m.control_rows                AS row_diff,
       CASE WHEN m.control_rows IS NULL        THEN 'NO_CONTROL_FILE'
            WHEN m.rows_loaded = m.control_rows THEN 'OK'
            ELSE 'MISMATCH' END                 AS recon_status
FROM GYRUS_DW.ADMIN.LOAD_MANIFEST m
WHERE m.report_name = 'policy';

-- Which values failed to cast? Present in RAW, NULL after conversion.
-- This is the payoff for the all-text rule in step 6.
CREATE OR REPLACE VIEW GYRUS_DW.STAGING.V_CAST_FAILURES AS
SELECT _file_name, _file_row_number, policy_id,
       gross_premium AS raw_value, 'gross_premium' AS column_name
FROM GYRUS_DW.RAW_DUCKCREEK.POLICY_EXTRACT
WHERE TRIM(COALESCE(gross_premium, '')) <> ''
  AND TRY_TO_NUMBER(REPLACE(TRIM(gross_premium), ',', ''), 18, 2) IS NULL;

-- No control totals? Compare against the file's own recent history instead.
SELECT business_date, rows_loaded,
       AVG(rows_loaded) OVER (ORDER BY business_date
                            ROWS BETWEEN 7 PRECEDING AND 1 PRECEDING) AS avg_prev_7
FROM GYRUS_DW.ADMIN.LOAD_MANIFEST WHERE report_name = 'policy';

6.3  If the extracts arrive as Excel

Snowflake cannot read .xlsx. COPY INTO supports CSV, JSON, Avro, ORC, Parquet and XML — that is the whole list. Ask for CSV first; most reporting tools export it just as easily, and it removes an entire class of problems permanently.

If the answer is no, parse it inside Snowflake with a Python procedure — no external infrastructure to run or monitor.

Excel parsing, in Snowflake
CREATE OR REPLACE PROCEDURE load_xlsx(stage_path STRING, sheet STRING)
RETURNS STRING LANGUAGE PYTHON RUNTIME_VERSION = '3.11'
PACKAGES = ('snowflake-snowpark-python', 'openpyxl', 'pandas') HANDLER = 'run'
AS $$
import pandas as pd
def run(session, stage_path, sheet):
    stream = session.file.get_stream(stage_path, decompress=False)
    df = pd.read_excel(stream, sheet_name=sheet, engine='openpyxl',
                       dtype=str,      # all text — same rule as step 6
                       header=0)
    df = df.dropna(how='all')     # trailing phantom rows
    df.columns = [str(c).strip().lower().replace(' ', '_') for c in df.columns]
    df['_source_file'] = stage_path
    session.write_pandas(df, 'POLICY_EXTRACT_XLSX', schema='RAW_DUCKCREEK',
                         database='GYRUS_DW', auto_create_table=True,
                         overwrite=False)   # append — RAW is append-only
    return f'Loaded {len(df)} rows'
$$;

dtype=str matters for the same reason step 6 does, plus one more: it stops pandas inferring types differently between files, which would break the table schema on an ordinary Tuesday. It also preserves leading zeros and prevents large reference numbers becoming floats.

7.1  How to build it

Step 1

Land the whole JSON payload untouched

Snowflake has a native VARIANT type that stores JSON directly and lets you query into it with SQL. Store the entire response, not the fields you think you need.

Landing table
CREATE OR REPLACE TABLE GYRUS_DW.RAW_DUCKCREEK.API_POLICY (
    payload     VARIANT,        -- the entire response object
    endpoint    VARCHAR,
    page_no     NUMBER,
    fetched_at  TIMESTAMP_LTZ,
    request_id  VARCHAR         -- ties rows to one run, for debugging
);

Why keep the whole payload. If your flattening logic turns out to be wrong — wrong field, wrong nesting, missed an array — you rewrite a view and rebuild. If you had extracted only five fields at fetch time, you would have to re-call the API for every record, which may not even be possible for historical data.

Step 2

Flatten into a staging view

LATERAL FLATTEN turns a JSON array into rows. The : operator navigates into the object and :: casts the result.

Flattening
CREATE OR REPLACE VIEW GYRUS_DW.STAGING.STG_API_POLICY AS
SELECT
    f.value:policyId::VARCHAR                  AS policy_id,
    f.value:brokerRef::VARCHAR                 AS broker_ref,
    UPPER(TRIM(f.value:status::VARCHAR))      AS policy_status,
    TRY_TO_NUMBER(f.value:grossPremium::VARCHAR, 18, 2) AS gross_premium,
    TRY_TO_DATE(f.value:effectiveDate::VARCHAR)  AS effective_date,
    a.fetched_at
FROM GYRUS_DW.RAW_DUCKCREEK.API_POLICY a,
     LATERAL FLATTEN(input => a.payload:items) f
QUALIFY ROW_NUMBER() OVER (
    PARTITION BY f.value:policyId::VARCHAR
    ORDER BY a.fetched_at DESC) = 1;

The QUALIFY clause is doing heavy lifting here. API polling produces duplicates constantly — a retry after a timeout, overlapping pages, a re-run after a partial failure. Keeping only the newest row per policy makes all of that harmless.

Step 3

Track where you got to

An API poller must be resumable. Without a watermark, a failure halfway through means either re-fetching everything or silently missing a window.

Watermark
CREATE TABLE IF NOT EXISTS GYRUS_DW.ADMIN.API_WATERMARK (
    endpoint          VARCHAR,
    last_success_ts   TIMESTAMP_LTZ,  -- resume point
    last_cursor       VARCHAR,        -- provider pagination token
    consecutive_fails NUMBER DEFAULT 0,
    updated_at        TIMESTAMP_LTZ
);

Alert on consecutive_fails. A poller that has been failing quietly for three days looks identical to one that is working, because the warehouse still has data in it — just increasingly stale data.

9.1  What CDC is, and why it beats re-reading tables

Two ways to keep a warehouse in sync with a database. Full refresh re-reads every table on every run: simple, but slow, expensive, and it hammers the source. Change data capture reads the log the database already writes for its own replication and recovery, and replays those changes into the warehouse.

CDC wins on three counts: it is near-real-time, it puts almost no load on the source (it is reading a log file, not scanning tables), and — uniquely among all five routes — it captures deletes.

The two engines expose this differently, which changes what you have to configure.

SQL Server — Change Tracking
-- Database level. No restart required.
ALTER DATABASE gyrus SET CHANGE_TRACKING = ON
    (CHANGE_RETENTION = 7 DAYS, AUTO_CLEANUP = ON);

-- Per table — and tables WITHOUT a primary key are silently skipped.
-- Find them BEFORE you plan the load:
SELECT s.name, t.name FROM sys.tables t
JOIN sys.schemas s ON t.schema_id = s.schema_id
WHERE NOT EXISTS (SELECT 1 FROM sys.indexes i
                  WHERE i.object_id = t.object_id AND i.is_primary_key = 1);

ALTER TABLE dbo.quote ENABLE CHANGE_TRACKING WITH (TRACK_COLUMNS_UPDATED = OFF);

-- Read-only replication login
CREATE LOGIN snowflake_cdc WITH PASSWORD = '<strong>';
CREATE USER  snowflake_cdc FOR LOGIN snowflake_cdc;
GRANT SELECT               ON SCHEMA::dbo TO snowflake_cdc;
GRANT VIEW CHANGE TRACKING ON SCHEMA::dbo TO snowflake_cdc;  -- the forgotten one
MySQL — binary log
-- Must be ROW format. STATEMENT records the SQL text, which cannot be
-- reliably replayed into a different system.
SHOW VARIABLES LIKE 'binlog_format';      -- want ROW
SHOW VARIABLES LIKE 'binlog_row_image';   -- want FULL

-- On RDS these live in a parameter group and REQUIRE A REBOOT to take effect.
-- Schedule that. Multi-AZ failover is typically 60–120 seconds.
CALL mysql.rds_set_configuration('binlog retention hours', 168);

CREATE USER 'snowflake_cdc'@'10.0.1.%' IDENTIFIED BY '<strong>';
GRANT SELECT ON gyrus.* TO 'snowflake_cdc'@'10.0.1.%';
GRANT REPLICATION SLAVE, REPLICATION CLIENT ON *.* TO 'snowflake_cdc'@'10.0.1.%';

Note what those grants do not include: no INSERT, UPDATE or DELETE. The replication account is strictly read-only against the data. Verify that before handing credentials to anyone.

Deleted records are the commonest cause of a warehouse that is confidently wrong. Three of the five routes lose them unless we build for it.

For a broker this is not academic. A cancelled policy that lingers inflates in-force counts, gross written premium and commission. Nothing errors. The dashboard renders, the query succeeds, the number is wrong, and it stays wrong until someone reconciles against the source by hand.

The test

10.2  Deriving deletions from consecutive snapshots

If we take Route B and need to know when something was cancelled rather than just excluding it, compare each snapshot with the one before.

Snapshot diff
CREATE OR REPLACE VIEW GYRUS_DW.MARTS.V_POLICY_DISAPPEARANCES AS
WITH dates AS (
  SELECT DISTINCT snapshot_date,
         LAG(snapshot_date) OVER (ORDER BY snapshot_date) AS prev_date
  FROM GYRUS_DW.STAGING.STG_POLICY_SNAPSHOTS
)
SELECT d.snapshot_date AS disappeared_on, p.policy_id
FROM dates d
JOIN      GYRUS_DW.STAGING.STG_POLICY_SNAPSHOTS p ON p.snapshot_date = d.prev_date
LEFT JOIN GYRUS_DW.STAGING.STG_POLICY_SNAPSHOTS c
       ON c.snapshot_date = d.snapshot_date AND c.policy_id = p.policy_id
WHERE d.prev_date IS NOT NULL
  AND c.policy_id IS NULL;   -- present yesterday, absent today
Never act on this view alone

A row disappearing might mean deleted — or the export filter changed, or the report ran for a narrower date range, or the file was truncated. A truncated extract is indistinguishable from a mass cancellation event. Always confirm the file reconciled (§06 step 8c) before treating disappearances as deletions. Getting this backwards turns a reporting glitch into a business incident.

The Gyrus dimensional model

Whatever route wins, this is what MARTS should look like. Facts record events — a policy version, a payment, a claim. Dimensions describe the things you filter and group by — broker, product, date. This star-shaped arrangement is what BI tools expect and what non-engineers can reason about.

The grain decisions below matter more than the SQL. Grain means “what does one row represent?”, and getting it wrong is expensive to unwind once reports depend on it.

The version-grain fact
CREATE OR REPLACE DYNAMIC TABLE GYRUS_DW.MARTS.FCT_POLICY_VERSION
  TARGET_LAG = '1 hour' WAREHOUSE = TRANSFORM_WH
AS
SELECT
    p.policy_id, p.policy_version,
    p.broker_ref, p.product_code, p.policyholder_id,
    p.policy_status,
    p.gross_premium, p.commission_amount,
    p.gross_premium - p.commission_amount    AS net_premium,
    p.effective_date, p.expiry_date,
    DATE_TRUNC('month', p.effective_date)   AS effective_month,
    b.broker_name, b.channel,                -- denormalised deliberately
    ROW_NUMBER() OVER (PARTITION BY p.policy_id
                       ORDER BY p.policy_version DESC) = 1 AS is_current_version
FROM GYRUS_DW.STAGING.STG_POLICY  p
LEFT JOIN GYRUS_DW.STAGING.STG_BROKER b ON p.broker_ref = b.broker_ref;

Three choices in that statement are worth explaining, because each runs against normal OLTP instincts:

  • Denormalising broker_name onto the fact. In a columnar store, wide tables are cheap — a query that does not reference a column does not read it — while runtime joins are the expensive part. The opposite of what you would do in Postgres, and correct here.
  • LEFT JOIN, never INNER JOIN. The two sides come from independently extracted sources. A policy written after the broker extract ran would silently vanish from an inner join. A left join keeps it visible with a null broker, and the orphan test below makes the gap countable.
  • is_current_version as a flag. Analysts asking “how many policies are in force?” should not have to write a window function. Give them a boolean.
Quality tests — schedule these, do not run them once
-- Grain integrity. If this returns rows, every SUM in every report is wrong.
SELECT policy_id, policy_version, COUNT(*)
FROM GYRUS_DW.MARTS.FCT_POLICY_VERSION GROUP BY 1,2 HAVING COUNT(*) > 1;

-- Orphans: the cost of LEFT JOIN discipline, made visible
SELECT COUNT(*) AS orphan_policies
FROM GYRUS_DW.MARTS.FCT_POLICY_VERSION f
LEFT JOIN GYRUS_DW.MARTS.DIM_BROKER d USING (broker_ref)
WHERE d.broker_ref IS NULL;

-- Business rule: premium should not be negative outside cancellations
SELECT COUNT(*) FROM GYRUS_DW.MARTS.FCT_POLICY_VERSION
WHERE gross_premium < 0 AND policy_status <> 'CANCELLED';

-- Freshness. Publish this on every dashboard so staleness is visible.
CREATE OR REPLACE VIEW GYRUS_DW.MARTS.V_DATA_FRESHNESS AS
SELECT MAX(_load_ts) AS last_load,
       DATEDIFF('hour', MAX(_load_ts), CURRENT_TIMESTAMP()) AS hours_stale
FROM GYRUS_DW.STAGING.STG_POLICY;
Publish freshness where users will see it

Users of a batch-fed warehouse will assume it is live unless told otherwise. Putting V_DATA_FRESHNESS on every dashboard is the cheapest way to stop someone acting on yesterday’s numbers believing they are this morning’s.

If Clarity carries a licence fee, do not weigh it against zero. Security and PII

Policyholder data is personal data and often special-category. Several of these controls are far cheaper to apply before the first row moves than to retrofit afterwards.

  • Exclude at source before masking downstream. A column never extracted cannot leak. Ask Duck Creek to omit fields we do not need — that beats any policy we could write.
  • Route A has the strongest posture by default — no copy of policyholder data in transit or at rest in a second system. Worth weighing alongside the engineering argument, not just after it.
  • Key-pair or managed identity for service accounts, never passwords. Snowflake supports two registered public keys simultaneously so you can rotate with no downtime.
  • Producer credentials write-only on Route B — one prefix, no read, no delete.
  • Network policy restricting service accounts to known IP ranges; MFA or SSO for every human user.
Masking and row-level access
-- PII concentrated in DIM_POLICYHOLDER, so mask once rather than per fact
CREATE MASKING POLICY mask_pii AS (val STRING) RETURNS STRING ->
  CASE WHEN CURRENT_ROLE() IN ('PII_READER', 'COMPLIANCE') THEN val
       ELSE '***MASKED***' END;

ALTER TABLE GYRUS_DW.MARTS.DIM_POLICYHOLDER
  MODIFY COLUMN email SET MASKING POLICY mask_pii;
ALTER TABLE GYRUS_DW.MARTS.DIM_POLICYHOLDER
  MODIFY COLUMN date_of_birth SET MASKING POLICY mask_pii;

-- Brokers see only their own book
CREATE ROW ACCESS POLICY broker_own_book AS (broker_ref VARCHAR)
RETURNS BOOLEAN ->
  CURRENT_ROLE() = 'INTERNAL_ANALYST'
  OR broker_ref IN (SELECT broker_ref FROM GYRUS_DW.ADMIN.USER_BROKER_MAP
                     WHERE snowflake_user = CURRENT_USER());

ALTER TABLE GYRUS_DW.MARTS.FCT_POLICY_VERSION
  ADD ROW ACCESS POLICY broker_own_book ON (broker_ref);

A masking policy is evaluated at query time based on the active role, so the same view returns different values to different people — no duplicate tables, no separate reporting layer. A row access policy does the same for whole rows, which is how you let brokers self-serve without exposing each other’s books.

Ask Q12 before the first row moves

Data residency, retention and masking obligations. Discovering a residency constraint after replicating a year of policyholder data is expensive to unwind — and on Route A it may also determine which region our Snowflake account has to live in, which is a decision made in week one.

How to select — the framework

Two separate questions get confused in conversations like this one: which route is best, and which routes are available. Answer them in that order.

Scoring tells you what to want. Availability tells you what you can have. That is why the outcome below is a gated ladder rather than a ranking — we pursue the highest-scoring route that survives the availability test, and we find out which those are by asking §16.

14.1  The six dimensions, and what they mean

DimensionThe question it answersWeight

Build effortHow long until the first trustworthy report? Weeks of engineering before any value appears.20%
IndependenceHow exposed are we if the vendor relationship changes? Can we keep operating?15%

Why those weights, for us specifically. Ops burden leads because we are a small team and it is the only cost that never stops — a route that needs a person watching it every morning is more expensive in year two than a licence fee. Completeness ranks high because this is regulated financial data where a silently wrong in-force count is a serious problem, not a cosmetic one. Freshness ranks low because broker reporting is a daily-cadence business; nobody is making underwriting decisions on five-minute-old data.

14.4  The gate — four questions in order

Work down this list and stop at the first yes. Each question is answered by a specific item in §16.

Q1Entitlement

Are we licensed for Clarity, or can we be at acceptable cost?

Yes → Route A. Stop evaluating.

Nothing else competes on score. If we are not licensed, get a price before dismissing it — and weigh that price against §12’s comparison, which counts the permanent operational load of the alternatives, not just their build cost.

Q2Extracts

Will they deliver scheduled extracts to a bucket we own?

Yes → Route B. Settle format, cadence, grain and control totals in the same conversation.

This is the likeliest yes of all five, which is why it is the primary fallback. Build it with the control plane from §06 step 8 included from the start — retrofitting it after the first incident is how these pipelines get a bad reputation.

Q3Hosting

Is our Duck Creek instance self-hosted rather than vendor-hosted?

Yes → Route E becomes available and jumps up the list.

If we host it, database access is ours to grant. Ask for a read replica rather than production, and expect to justify the load. Note this reordering only happens on a yes — on vendor-hosted SaaS the question closes permanently.

Q4Fallback

All three answered no?

Route C, scoped deliberately narrow, with a review date set at creation.

Take the entities that carry real reporting value, accept that history and deletes are limited, document those limits where analysts will actually encounter them, and keep pressing Q1 and Q2 in parallel. The failure mode to guard against is a tactical pipeline quietly becoming the permanent architecture because nobody ever revisited it.

Check D at the same time, not after

Route D is not a rung on this ladder — it is a modifier on B and C. Send one internal email asking whether we already license a connector platform. If yes, it makes whichever of B or C we land on materially cheaper to operate. If no, ignore it.
